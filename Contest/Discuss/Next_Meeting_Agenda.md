## 4｜主要使用者與 Persona（Q4，10 分鐘）

| 選項 | 主軸 |
|---|---|
| a. 營運優先 | 減少人工看照片、提早攔截異常 |
| b. 用戶優先 | 拍照更順、不再接到髒車 |
| **c. 雙邊信任（建議）** | 營運效率為主軸，以「歸責公平透明」連結用戶 |

**補充決策：Persona 各選一位**

| 角色 | 建議 Persona | 痛點 |
|---|---|---|
| 用戶 | 隨租隨還的通勤族，常在地下停車場取還車 | 光線差拍不好被要求重拍；接到上一手髒車；擔心被誤判車損 |
| 營運 | 後台車況審核員＋外勤整備人員 | 大量照片人工逐張看；異常發現太晚；清潔派工靠人工判斷 |

佐證：媒體報導指出隨租隨還車輛停放分散、維護較不穩定；也有用戶取車未拍照，還車時被認定車損由其負擔的案例（以前一位用戶的照片判斷）。

**要決定：** 採用哪個主軸？Persona 是否採用？提案摘要「目標對象」一句話怎麼寫？

## 5｜方案範圍與規則（新增，15 分鐘）

「解決方案設計」頁需要以下具體規則；建議值供討論，若解題資源中的「照片上傳清單」已有規定，以官方為準：

| # | 規則 | 建議 |
|---|---|---|
| R1 | 必拍清單 | 依 iRent 官方上傳清單；車外以「前、後、左、右、四個斜角」為基準，車內「前座、後座、儀表板」 |
| R2 | 即時防呆檢查項目（環節一） | 模糊、過暗（需開閃光燈提示）、視角錯誤、車牌未入鏡、距離過遠／過近、鏡頭髒汙；不合格即時提示原因並引導重拍 |
| R3 | 整潔三級定義（環節二） | 乾淨＝無可見垃圾與污漬；普通＝少量灰塵或輕微雜物、不影響下一位使用；髒汙＝垃圾、食物殘渣、液體污漬、異味來源或遺留物 → 立即預警 |
| R4 | 新車損預警門檻（環節二） | 取還車同視角比對出現新增損傷即建工單；依疑似程度分「需人工確認」與「明顯新損」兩級 |
| R5 | 通知與派工（環節三） | 後台儀表板依嚴重度排序；髒汙車輛自動暫停出租並派清潔；建議目標：還車後 5 分鐘內產生預警 |
| R6 | 下一位用戶保護 | 被標記為髒汙或待確認車損的車輛，不出現在可租清單，或在取車前顯示已知車況 |

**要決定：** R1–R6 是否採用？哪些數字（如 5 分鐘）要放進簡報？

## 6｜AI 架構、Demo 與資料使用（Q5，15 分鐘）

| 選項 | 簡報描述的架構 | Demo |
|---|---|---|
| a. 完整架構 | 手機端品質閘門＋雲端專用模型＋取還車比對＋VLM＋人工 | 同左（來不及） |
| b. 只用 VLM | 全部交給 Gemini 判讀 | Gemini API |
| **c. 目標架構＋MVP（建議）** | 完整目標架構，每層附引用 | Gemini API 做品質檢查與整潔判讀，取還車比對用一組照片示範 |

**補充決策：**

| # | 問題 | 建議 |
|---|---|---|
| D1 | Demo 形式 | 單頁網頁或 Streamlit：上傳照片 → 顯示品質判定與整潔等級；比對畫面可用預先跑好的結果 |
| D2 | **解題資料能否送外部 API** | 保守做法：demo 只用**公開圖片或團隊自拍照片**；iRent 提供的照片只用於分析與簡報示意。必要時寄信向主辦確認 |
| D3 | Demo 是否放上 GitHub | 建議放（官方模板「補充資料」頁列有 GitHub），但只放程式碼，不放解題資料 |
| D4 | 提案摘要「AI 技術、服務或模型」欄位 | Gemini（VLM 判讀與報告生成）、車損分割模型（以 CarDD 預訓練）、變化偵測、手機端影像品質模型 |

## 7｜收費政策與申訴（Q8，5 分鐘）

**提案：** AI 不單獨收費：疑似新車損自動建立工單並附取還車對照證據，營運人員確認後才收費；用戶在 App 可查看證據並申訴。

**建議：** 採用，並放進「獨特優勢與差異化」頁，與 Hertz 案例對照。

## 8｜車況接力：誘因與防弊（新增，10 分鐘）

| # | 問題 | 建議 |
|---|---|---|
| I1 | 誰得到獎勵 | 取車時回報「上一手髒汙／新損傷」且經 AI＋人工確認屬實的用戶 |
| I2 | 獎勵內容 | 和泰 Points 或租車折抵（數額先寫「待與 iRent 定義」） |
| I3 | 防止謊報 | 獎勵須通過 AI 判讀＋人工確認；同一車次只獎勵第一位；異常頻繁回報的帳號列入觀察 |
| I4 | 對上一手的處理 | 依既有清潔費規則；同樣適用「AI 不單獨收費」 |

## 9｜KPI 與效益估算（新增，10 分鐘）

**公開基準：** iRent 會員突破 200 萬、累積租借超過 2,000 萬次、約 2,000 個據點（媒體報導）。

| KPI | 定義 | 目標（待討論） |
|---|---|---|
| 人工審照片時數 | 每日營運人員看照片的工時 | 減少 60–80%（只需複核 AI 標記的異常） |
| 異常攔截時間 | 還車到產生預警的時間 | 從「人工看到才知道」降到 5 分鐘內 |
| 重拍率／照片不合格率 | 上傳照片需重拍的比例 | 照片一次合格率提升，後台補件歸零 |
| 髒車客訴數 | 每月「接到髒車」客訴 | 減少 50% |
| 車損爭議案件數 | 每月車損責任爭議 | 減少 50%（以取還車對照證據） |

**要決定：** 目標數字寫範圍還是單一數值？是否附上 Gemini API 成本試算（每次還車約 10 張照片）？
